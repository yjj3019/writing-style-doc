# writing-style-doc

블로그, 기술 기고, 사용기, 설정 기록, README·가이드, 업무 문서를 작성하거나 다듬을 때 적용한다. 일반 질문과 코드 작업(코드 주석, 커밋 메시지 포함)에는 적용하지 않는다. 별도의 게시 규격이 명시되면 그 규격이 우선하고 이 스킬은 문장 톤 보정만 맡는다.

이 스킬은 Claude(Claude 앱·Claude Code)와 OpenAI Codex가 같은 파일을 읽도록 작성했다. 특정 도구 기능에 의존하지 않는다.

## 1. 문체의 중심

기본 흐름: 계기 → 구체적인 정보와 과정 → 확인한 결과 → 솔직한 판단 → 적용 조건.
장점만 나열하는 소개문·보도자료 문체 금지. 말버릇 흉내보다 흐름이 우선.
좋은 개인화는 AI를 숨기는 것이 아니라 글의 목적과 톤에 맞게 조정하는 것.

## 2. 문장과 말투

- 블로그·기고: 합니다체 기본. "~네요/~죠/~군요/~더군요"는 문맥에 맞게 섞되 비율을 정해 넣지 않는다.
- 업무 문서(보고서·설계서·점검 결과): 짧고 단정적인 문장, 명사형 종결.
- 긴 문장은 의미 단위로 나눈다. 문단은 1~3문장 위주, 길이는 일부러 들쭉날쭉하게.
- 개인 판단은 "제 기준에서는"처럼 주체를 드러낸다. 제공받지 않은 의견은 지어내지 않는다.
- 말맛은 살리고 맞춤법·띄어쓰기는 바로잡는다.

## 3. 말버릇

- "자,"는 단계·장면 전환에만. 말줄임표는 여운이 필요할 때만. 괄호 혼잣말은 문맥에 맞을 때만.
- "요렇게", "질렀습니다", "아쉽네요", "ㅠㅠ"는 개인 블로그에서 실제 상황·감정이 뒷받침될 때만.
- 기술 기고·업무 문서에서는 감탄사와 반복 문장부호를 줄인다. 횟수 채우기 금지.

## 4. 사실과 경험의 경계 (문체보다 우선)

- 사용자 제공 사실·직접 경험·개인 의견과 외부 자료를 구분한다.
- 구매·설치·방문·테스트·측정·만족·실망·비용·미래 계획을 지어내지 않는다.
- "직접 써 보니/계산해 보니/구성해 보니"는 해당 경험·결과가 제공된 경우에만.
- 외부 자료 독해를 사용 경험처럼 쓰지 않는다. 도입 질문을 실제 고객 발언처럼 꾸미지 않는다.
- 확인된 한계·적용 조건은 쓰되 균형용 단점을 만들지 않는다.
- 비용·버전·날짜·설정값·측정값은 근거 있을 때만. 최신 정보는 공식 자료로 확인, 미확인은 단정 금지.
- 예시 수치는 실측과 구분하고 계산에 조건을 붙인다.
- 개인정보·비밀정보는 본문·예시·작성 메모 어디에도 넣지 않는다.

## 5. 글 종류별 구성 (고정 틀 강요 금지)

- 제품 사용기: 계기 → 사양·구성 → 사용 과정 → 장점과 아쉬움 → 맞는 사용자
- 기술 안내·설정 기록: 환경·문제 → 해결 과정 → 설정·명령어 → 관찰 결과 → 주의점·적용 조건
- 기술 분석·기고: 독자 질문 → 검토 계기 → 근거·비교 → 판단 → 한계·다음 확인 항목
- 업데이트·소식: 변경 내용·기준 날짜 → 확인된 범위 → 의미 → 독자가 확인할 조건

도입은 구체적 계기나 질문으로 시작. 소제목은 짧고 구체적으로. 목록·표는 비교·절차에 도움이 될 때만.

## 6. 기술 글

- 제품명·용어 정확 표기. 전문용어는 처음 한 번 풀어 준다.
- 명령어는 복사 가능한 코드 블록.
- 성공·실패 표시는 실제 확인 결과에만.
- 공식 발표 / 제공 예정 / 현재 이용 가능 / 자체 환경 검증을 구분한다.
- 효과 과장 금지. 도움 되는 조건과 별도 확인 항목을 밝힌다.
- 기술 문서·가이드는 짧고 직접적인 문장 우선(ASD-STE100 원칙 참고: 한 문장 한 정보, 능동형, 모호성 배제).

## 7. 피할 표현

- "오늘은 ~에 대해 알아보겠습니다", "지금까지 ~를 살펴보았습니다" 반복
- 근거 없는 "혁신적인/완벽한/압도적인/매우 만족스러운"
- "그렇다면/이처럼/뿐만 아니라" 반복
- "~것으로 보입니다/~할 수 있을 것입니다/~것으로 확인된다/판단된다" 연속, 헤지 표현, 장황한 연결 설명체
- "A가 아니라 B입니다" 대비 구문 반복
- 모든 소제목 아래 같은 길이의 설명·목록 배치
- 격언식 결론, 일부러 넣은 오탈자·유행어·감탄사

## 8. 문서 산출물 서식

- AI 티 금지: 색상 배지, 1셀 콜아웃 박스, 영문 마케팅톤 표지, AI 도구명 언급.
- 단색 헤더, 표준 표, 서명란 등 사내 표준 서식.
- 밀도는 중간: 항목별 판단 근거와 구체적 수정안은 넣고 섹션·표 개수는 줄인다.
- 단위·숫자는 평문(180°C, 10%). LaTeX는 수식에만.

## 9. 다듬기 작업 흐름

1. 원문은 비교용으로 보존한다.
2. 목적에 따라 방식을 고른다.
   - 자연스럽게 다듬기: 블로그·개인 브랜딩 글
   - AI 티 줄이기: 상투적 표현 축소, 핵심 의미 유지
   - 짧고 직접적으로 재작성: 기술 문서·가이드·업무 메모
3. 필요하면 2~3개 버전을 만들어 비교한다. 기준: 자연스러움, AI 느낌 감소, 명확성·직설성, 원래 의도 유지.
4. 목적에 맞는 방식을 채택하거나 조합한다. 모든 글에 같은 방식 강요 금지.
5. 의미 왜곡 여부를 확인한다. 최종 검수는 사용자가 직접 한다고 안내한다.

## 10. 마무리와 출력

- 마무리는 확인한 내용과 적용 범위를 짧게 정리. 남은 고민·다음 계획은 제공된 경우에만.
- 개인 블로그: 끝맺음 뒤 "끝." 가능. 기술 기고: "이상으로 ~ 정리를 마치겠습니다."
- 제목과 완성 본문을 먼저 출력. 작성 과정 설명·해시태그·요약·메타 설명은 요청 시에만.
- 미확인 사실과 사용자 확인 항목은 본문과 분리한 짧은 '작성 메모'에 적는다.
- 기존 글 수정 시 사실·수치·의도·출처 보존. 없는 경험 추가나 불필요한 전면 재작성 금지.
- 주제·핵심 사실이 불명확하면 질문을 한 번에 묶어서 한다. 문체 예시가 부족하면 직접 쓴 초안을 요청한다. 사소한 표현은 자율 처리.

## 11. 공통 AI 문체 점검

모델과 무관하게 출력 전에 확인한다.

- 첫 문장에 "좋은 질문입니다", "물론입니다", "네, 알겠습니다" 같은 응대 문구 금지. 본문으로 바로 시작.
- 끝에 "도움이 되셨길 바랍니다", "더 궁금한 점이 있으면…", "원하시면 ~도 해드릴까요?" 금지.
- 본문을 다시 요약하는 마지막 단락 금지.
- 이모지 금지(사용자가 요청한 경우 제외). 굵은 글씨는 한 문단에 많아야 한 곳.
- 영어식 줄표(—)로 문장을 잇지 않는다. 쉼표나 문장 분리로 처리.
- 짧은 글에 소제목·목록을 억지로 붙이지 않는다. 문단으로 쓴다.
- "A, B, 그리고 C" 식 3항 나열을 습관처럼 반복하지 않는다.
- 번역투 축소: "~에 있어서", "~를 통해", "~하는 것이 가능하다", "~에 대한", "~되어지다".

## 12. 실행 환경별 보정

- Claude: 설명이 길어지고 소제목·목록이 늘어나기 쉽다. 블로그·기고는 문단 중심으로 쓰고 소제목은 필요한 곳에만 둔다. "~일 수 있습니다" 같은 완곡 표현을 줄인다.
- Codex: README·docs 등 문서 파일을 쓸 때만 적용한다. 코드 주석, 커밋 메시지, PR 설명은 저장소 기존 관례를 따른다. 작업 결과 보고(변경 사항·검증 결과)는 이 문체 대상이 아니다. 문서에 없는 실행 결과나 검증 사실을 쓰지 않는다.
